# 아키텍처 설계 (A-SPICE SWE.2)

## 핵심 원칙
**컴포넌트는 인터페이스를 통해서만 서로 통신한다.** 인터페이스가 없는 컴포넌트는 정의된 것이 아니다.

## 절차
1. 소프트웨어 요구사항(`SWR`)을 읽고 책임 단위로 컴포넌트를 나눈다.
2. 컴포넌트마다 ID(`ARCH-xxx`), 책임 한 문장, 할당된 `SWR` 목록을 적는다.
3. 컴포넌트마다 **인터페이스를 반드시 정의**한다 (아래 형식).
4. 컴포넌트 간 의존 관계를 인터페이스 단위로 그린다. 인터페이스를 거치지 않는 연결은 설계에서 제거한다.
5. 동적 동작(초기화, 주기 실행, 오류 처리 순서)을 필요한 만큼 기술한다.
6. 설계 결정마다 근거와 대안을 남긴다.
7. 추적성 매트릭스를 갱신하고 `review` 스킬로 리뷰한다.

## 인터페이스 정의 형식

| 필드 | 내용 |
|---|---|
| ID | `IF-xxx` |
| 제공 컴포넌트 / 사용 컴포넌트 | 누가 제공하고 누가 쓰는가 |
| 함수 시그니처 | 이름, 매개변수(방향 in/out, 단위, 범위), 반환 타입 |
| 반환값 의미 | 정상/오류 코드 목록 |
| 사전/사후 조건 | 호출 전 보장, 호출 후 보장 |
| 호출 규칙 | 호출 순서, 주기, 재진입성, 스레드/인터럽트 안전성 |
| 오류 처리 | 실패 시 호출자가 해야 할 일 |

## 설계 품질 기준

| 기준 | 확인 방법 |
|---|---|
| 높은 응집도 | 컴포넌트 책임을 한 문장으로 쓸 수 있는가. "및"이 필요하면 분리를 검토한다. |
| 낮은 결합도 | 컴포넌트가 다른 컴포넌트의 내부 데이터·함수를 직접 쓰지 않는가. 의존은 인터페이스 하나로 좁혔는가. 순환 의존이 없는가. |
| 모듈화 | 컴포넌트를 독립적으로 구현하고 시험할 수 있는가. |
| 캡슐화 | 내부 상태와 구현은 감추고 인터페이스만 노출하는가. 전역 변수 공유가 없는가. |
| S 단일 책임 | 변경 이유가 하나인가. |
| O 개방-폐쇄 | 새 기능을 기존 컴포넌트 수정 없이 추가할 수 있는가. |
| L 리스코프 치환 | 인터페이스 구현체끼리 바꿔 써도 계약이 유지되는가. |
| I 인터페이스 분리 | 사용자가 쓰지 않는 함수를 억지로 의존하게 하지 않는가. |
| D 의존 역전 | 상위 컴포넌트가 하위 구현이 아니라 인터페이스(추상)에 의존하는가. |

SOLID는 C에서도 함수 포인터 테이블, 헤더 분리, 불투명 타입(opaque type)으로 적용한다.
