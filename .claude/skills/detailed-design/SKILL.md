# 상세 설계 (A-SPICE SWE.3)

## 핵심 원칙
아키텍처 컴포넌트(`ARCH`)를 구현 가능한 **모듈(`MOD`)** 로 나누고, 인터페이스가 정의된 모듈은 **그 인터페이스를 통해서만** 통신한다.

## 절차
1. 컴포넌트의 책임과 인터페이스(`IF`)를 입력으로 받는다.
2. 컴포넌트를 모듈(`MOD-xxx`, 소스 파일/헤더 쌍 단위)로 나눈다.
3. 모듈마다 책임 한 문장과 상위 `ARCH`/`SWR`을 적는다.
4. 인터페이스 정의 대상 판단: 아래 기준에 해당하면 인터페이스를 반드시 정의한다.
5. 모듈 내부의 주요 함수(`FUNC-xxx`)에 대해 동작, 입출력, 오류 처리를 기술한다.
6. 정적 데이터와 상태 변수의 소유 모듈을 정한다.
7. 추적성을 갱신하고 `review` 스킬로 리뷰한다.

## 인터페이스 정의 기준 ("특정 수준 이상의 모듈")
다음 중 **하나라도** 해당하면 인터페이스를 정의한다. 기준은 프로젝트에서 바꿀 수 있고, 바꾸면 이 표를 수정한다.
- 다른 모듈이 호출하는 함수가 둘 이상이다.
- 컴포넌트 인터페이스(`IF`)를 구현하거나 제공한다.
- 상태(static 데이터)를 소유한다.
- 하드웨어·OS 등 외부 자원에 접근한다.

인터페이스가 있는 모듈은 헤더에 공개 함수만 선언하고, 내부 함수와 데이터는 `static`으로 숨긴다. 다른 모듈의 `.c` 내부, 전역 변수, `extern` 데이터를 직접 쓰지 않는다.
기준에 해당하지 않는 작은 모듈은 인터페이스 없이 둘 수 있지만 그 판단을 상세 설계에 기록한다.

## 클린코드 원칙 적용

| 원칙 | 설계 시 확인 |
|---|---|
| 의미 있는 이름 | 이름만으로 의도가 드러나는가. 약어와 매직 넘버가 없는가. |
| 작은 함수 | 한 함수가 한 가지 일을 하고 한 추상화 수준에 머무는가. 설계한 동작이 **순환복잡도 10 이하, 80라인 이하**로 구현될 크기인가 (`CLAUDE.md` 2.3). 넘을 것 같으면 설계 단계에서 함수를 나눈다. |
| **단일 책임** | 모듈과 함수 모두 변경 이유가 하나인가. |
| 매개변수 최소화 | 매개변수가 많으면 구조체로 묶거나 책임 분리를 검토한다. |
| 부수효과 분리 | 계산과 상태 변경, 입출력을 분리했는가. |
| 중복 제거 (DRY) | 같은 로직이 두 곳에 없는가. |
| 주석 | 이유(why)를 쓰고, 코드가 말하는 내용을 반복하지 않는다. |
| 오류 처리 | 모든 실패 경로에 처리 방침이 있는가 (`implementation` 스킬의 반환값 규칙과 일치). |

## 함수 설계 항목

| 필드 | 내용 |
|---|---|
| ID / 이름 | `FUNC-xxx` / 함수명 |
| 책임 | 한 문장 |
| 입력 / 출력 | 타입, 단위, 유효 범위 |
| 반환값 | 정상·오류 값 목록 (void 금지, `implementation` 스킬 참조) |
| 동작 | 의사코드 또는 상태 전이 |
| 오류 처리 | 실패 경로별 동작 |
| 추적 | `MOD`, `ARCH`, `SWR` |
