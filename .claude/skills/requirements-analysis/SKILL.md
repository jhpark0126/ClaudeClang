# 요구사항 분석 (A-SPICE SWE.1)

## 핵심 원칙
모든 요구사항은 **분류되고, 검증 가능하며, 이후 산출물과 양방향 추적**되어야 한다.

## 분류 체계

```
요구사항
├── 기능 요구사항 (Functional)
│   └── 기능 안전 요구사항 → 별도 문서(safety-requirements)에서 관리. 이 문서에 쓰지 않는다.
└── 비기능 요구사항 (Non-functional)
    ├── 품질 요구사항 → ISO 25010 특성으로 분류
    ├── 제한 요구사항 (Limit): 수치 한계 (메모리, 처리시간, 주기)
    └── 제약사항 (Constraint): 언어, 표준, 도구, 플랫폼, 법규
```

기능 안전 요구사항은 본문에 쓰지 않고 `SSR-xxx` ID로 별도 문서를 가리키는 참조만 남긴다.

## ISO 25010 품질 특성 (품질 요구사항은 반드시 하나를 지정)
기능 적합성(완전성/정확성/적절성), 성능 효율성(시간 반응/자원 사용/용량), 호환성(공존/상호운용성), 사용성, 신뢰성(성숙성/가용성/결함 허용/복구성), 보안성, 유지보수성(모듈성/재사용성/분석성/변경성/시험성), 이식성.

## 요구사항 작성 규칙
1. 한 요구사항은 하나의 사항만 말한다. "그리고"로 이어진 문장은 분리한다.
2. "shall" 형태(`~해야 한다`)로 쓰고, 모호어(적절히, 빠르게, 충분히)를 쓰지 않는다.
3. 측정·시험 가능한 기준을 포함한다. 품질 요구사항은 수치와 측정 조건을 적는다.
4. 구현 방법이 아니라 필요한 동작과 성질을 기술한다.
5. 요구사항끼리 모순되지 않는지 확인한다.

## 요구사항 항목 형식

| 필드 | 내용 |
|---|---|
| ID | `SWR-F-001`(기능), `SWR-Q-001`(품질), `SWR-L-001`(제한), `SWR-C-001`(제약) |
| 설명 | shall 문장 하나 |
| 분류 | 기능 / 품질(ISO 25010 특성) / 제한 / 제약 |
| 출처 | 상위 요구사항 ID 또는 이해관계자 |
| 검증 기준 | 통과 조건 |
| 상위 추적 | 시스템 요구사항 ID 또는 `SSR-xxx` |
| 하위 추적 | `ARCH-xxx`, `UT-xxx`, `IT-xxx` (이후 단계에서 채움) |

## 양방향 추적성
- **상향:** 모든 `SWR`은 상위 요구사항/출처로 거슬러 올라갈 수 있어야 한다.
- **하향:** 모든 `SWR`은 최소 하나의 아키텍처 요소(`ARCH`)와 하나 이상의 시험(`UT`/`IT`)에 연결되어야 한다.
- 추적 매트릭스는 `docs/traceability.md`에 유지하고, 요구사항을 바꾸면 같은 변경에서 갱신한다.
- 연결되지 않은 요구사항, 요구사항 없이 존재하는 설계·코드·시험은 모두 결함이다.

## 산출물과 완료 조건
- 산출물: `docs/requirements/software-requirements.md`
- 완료 전 확인: 분류 누락 없음, 모든 항목에 검증 기준 있음, 추적 필드 채움, 다음 단계로 넘기기 전 `review` 스킬로 리뷰 완료.
