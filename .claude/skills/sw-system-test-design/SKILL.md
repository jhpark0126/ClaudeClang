# SW 시스템 테스트 케이스 설계

요구사항(테스트 베이시스)에서 **실행 가능한** 블랙박스 테스트 케이스를 도출하고, 추적성과 커버리지를 스크립트로 검증한 뒤 엑셀로 내보낸다.

이 스킬의 결과물은 A-SPICE 심사나 ISO 26262 기능안전 평가에서 증적(test specification)으로 쓰인다. 심사자는 "모든 요구사항이 테스트되었는가", "각 테스트가 어느 요구사항을 검증하는가", "테스트 케이스를 어떤 기법으로 도출했는가", "합격/불합격을 판정할 수 있는가"를 본다. 아래 규칙은 모두 이 네 질문에 답하기 위한 것이다. 표준별 상세 요건은 `references/standards.md`를 참고한다.

## 도구

- Python 3 + `openpyxl` (Windows에서 `python`이 PATH에 없으면 `py` 또는 `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`)
- 스크립트 경로는 이 SKILL.md가 있는 폴더 기준이다.
  - `scripts/pict_runner.py` — GitHub microsoft/pict 의 PICT를 찾거나 내려받아 실행
  - `scripts/build_workbook.py` — 테스트 케이스 JSON을 검증하고 엑셀로 생성

## 작업 순서

### 1. 입력 확인

필요한 것:
- **테스트 베이시스**: SW 요구사항 명세(SwRS), 인터페이스 명세, 안전 요구사항(TSR/SSR) 등. 파일이든 붙여넣은 텍스트든 된다.
- **테스트 케이스 양식** (선택): 사용자가 엑셀 양식을 주면 그 양식의 열을 그대로 쓴다. 없으면 기본 양식을 쓴다(아래 5단계).
- **ASIL 등급, 테스트 환경**(HIL, SIL, 실차 등) — 있으면 반영하고, 없으면 묻지 말고 `"HIL"` 같은 가정을 요약에 명시한다.

베이시스에 ID가 없으면 `REQ-001`처럼 부여하고 그 사실을 보고한다.

요구사항이 모호해서 **예상 출력값을 베이시스에서 정할 수 없으면 값을 지어내지 않는다.** 지어낸 기대값은 실행해도 판정이 의미 없기 때문이다. 대신 그 요구사항을 "질의 사항"으로 최종 보고에 남긴다. 판정 가능한 부분(예: 범위 밖 입력 거부)은 테스트 케이스로 만든다.

### 2. 베이시스 분석

각 요구사항을 **테스트 가능한 조건(condition)** 단위로 쪼갠다. 예: "차속 0~250 km/h 범위에서 100 ms 주기로 CAN 송신"은 (a) 값 범위, (b) 송신 주기 두 조건이다. 조건 ID는 `REQ-001-C1`처럼 붙인다. 이 조건 목록이 커버리지 100%의 분모가 된다.

각 조건을 기능/비기능으로 분류한다. 비기능은 타이밍/주기, 응답 시간, 자원(CPU, 메모리), 신뢰성/강건성, 안전 메커니즘(고장 검출·반응 시간), 보안, 진단 등이다. 하나의 요구사항이 둘 다 가지면 조건별로 나눈다.

각 조건마다 입력 파라미터와 그 도메인(타입, 범위, 단위, 해상도, 열거값), 출력과 관찰 방법을 정리한다.

### 3. 기법 적용

기법 상세와 예시는 `references/techniques.md`에 있다. 요약:

| 기법 | 적용 | 표기 |
|---|---|---|
| 동치 클래스 분할 | **필수**. 입력 도메인이 있는 모든 조건 | `동치 클래스 분할` |
| 경계값 분석 | **필수**. 순서가 있는 범위(수치, 시간, 길이, 개수)가 있는 모든 조건 | `경계값 분석` |
| 페어와이즈 | 서로 독립적인 파라미터가 3개 이상이고 조합 상호작용이 의심될 때. **반드시 PICT로 도출** | `페어와이즈(PICT)` |
| WoW 검증 | 엣지 상황 (아래 참고) | `WoW 검증` |
| 기타 | 요구사항 분석, 상태 전이, 결함 주입, 오류 추정 등 ISO 26262-6 기법은 필요 시 | 기법명 그대로 |

**동치 클래스**: 유효 클래스는 한 케이스에 여러 개를 묶어도 되지만, 무효 클래스는 한 케이스에 하나만 넣는다. 무효 입력이 둘이면 어느 쪽 때문에 거부됐는지 알 수 없기 때문이다.

**경계값**: 기본은 경계값과 바로 바깥 값(2-value). 안전 관련 요구사항(ASIL 지정)이나 경계 정의가 `<`/`≤`로 헷갈리는 경우에는 경계 안쪽 값까지 포함(3-value)한다. 바깥 값은 해상도(LSB) 한 단위만큼 떨어진 값이다. 해상도가 명시되지 않았으면 가정한 값을 비고에 쓴다.

**페어와이즈 (PICT)**: 손으로 조합을 만들지 않는다. 모델 파일을 쓰고 실행한다.

```
python scripts/pict_runner.py model.txt --json
```

처음 실행하면 GitHub 릴리스에서 `pict.exe`를 `bin/`에 받는다(Windows). PICT 실행이 불가능하면 페어와이즈를 생략하고 그 사실과 이유를 보고한다 — 손으로 만든 조합을 PICT 결과라고 표기하지 않는다. 불가능한 조합은 모델의 제약(`IF ... THEN ...;`)으로 제거한다. PICT 결과 각 행은 하나의 테스트 케이스가 되며, 각 행마다 베이시스에서 기대값을 도출해야 한다. 모델과 결과는 JSON의 `pict_models`에 넣어 엑셀에 증적으로 남긴다. 파라미터가 2개뿐이면 페어와이즈는 전수 조합과 같으므로 쓰지 않는다.

**WoW 검증 (엣지 상황)**: 경계값/동치 클래스로는 잡히지 않는 "설마 이런 상황이?" 를 검증한다. 예:
- 동작 중 전원 차단/저전압/재기동, 초기화 직후의 첫 입력
- 같은 주기 안에 겹치는 이벤트, 이벤트의 빠른 반복(토글), 최대 빈도 입력
- 신호 타임아웃, 값이 동결(freeze)된 신호, 범위 안이지만 비현실적인 급변
- 카운터/타이머 오버플로, 최대 길이·최대 개수 동시 적용
- 모드 전환 도중의 입력, 진단·고장 상태에서의 정상 요청

요구사항에서 근거를 댈 수 있는 엣지만 만든다. 근거 요구사항의 기대 동작(거부, 유지, 안전 상태 진입 등)으로 판정 가능해야 한다.

### 4. 테스트 케이스 작성 규칙

**실행 가능해야 한다.** 테스트 엔지니어가 추가 질문 없이 수행하고 합격/불합격을 판정할 수 있어야 한다.
- 입력값은 구체적인 값 + 단위 (`차속 = 120.0 km/h`, `0x1A3 신호 VehSpd = 0x0960`). "유효한 값", "큰 값" 금지.
- 사전조건: 초기 상태, 모드, 전원, 이전 입력 등.
- 절차: 번호를 매긴 단계. 각 단계는 하나의 행동.
- 예상 출력값: 관찰 가능한 값/상태 + 허용 오차 + 시간 조건 (`100 ms ± 10 ms 주기로 송신`). "정상 동작한다", "적절히 처리" 금지.

**쓰레기 케이스를 만들지 않는다.** 모든 케이스는 다른 케이스가 커버하지 않는 무언가(동치 클래스, 경계, 조합, 엣지)를 검증해야 한다. 같은 클래스의 값만 바꾼 케이스, 커버리지 숫자를 위해 조건을 억지로 나눈 케이스는 만들지 않는다. 케이스를 추가하기 전에 "이 케이스가 실패하면 다른 케이스로는 발견 못 한 결함을 알려 주는가?"를 자문한다.

**제안 케이스**: 베이시스가 직접 요구하지는 않지만 결함 발견에 가치가 있다고 판단해 추가하는 케이스(대부분의 WoW 검증, 요구사항 사이의 상호작용 등)는 `"suggested": true`로 표시한다. 엑셀의 `제안` 열에 "제안"으로 표시된다. 제안 케이스도 가장 관련 있는 베이시스 ID에 추적한다.

**ID 규칙**: 사용자 양식/규칙이 있으면 따른다. 없으면 기능 `STC-F-001`, 비기능 `STC-NF-001`.

### 5. JSON 작성 후 엑셀 생성

테스트 케이스를 JSON으로 저장한다 (형식은 `references/json_schema.md`). 그 다음:

```
python scripts/build_workbook.py cases.json -o <출력.xlsx> [--template <양식.xlsx>]
```

스크립트는 다음을 검사하고, **오류가 있으면 엑셀을 만들지 않고 종료 코드 1**로 끝난다:
- 모든 베이시스 ID와 조건 ID가 최소 하나의 케이스로 커버되는가 (커버리지 100%)
- 모든 케이스가 존재하는 베이시스/조건 ID를 참조하는가 (역방향 추적성)
- 케이스 ID 중복, 필수 항목 누락
- 동치 클래스 분할 / 경계값 분석이 사용되었는가

경고(생성은 됨)도 하나씩 확인한다: 모호한 기대값 표현, 입력·절차가 같은 중복 의심 케이스, 동치/경계값이 없는 베이시스 등. 경고가 정당하면(예: 입력 도메인이 없는 요구사항) 그 이유를 케이스 `notes`에 적는다.

오류가 0이 될 때까지 JSON을 고쳐서 다시 실행한다. 커버리지를 맞추려고 의미 없는 케이스를 추가하지 말고, 빠진 조건에 대해 실제로 검증할 케이스를 설계한다.

생성되는 시트: `기능 테스트`, `비기능 테스트`, `추적성 매트릭스`(베이시스/조건 → 케이스), `커버리지 요약`, `PICT 모델`(사용 시). 양식을 주면 양식의 첫 시트를 복사해 기능/비기능 시트를 만들고, 헤더 이름으로 열을 매핑한다. 매핑되지 않은 양식 열은 스크립트가 알려 주므로 사용자에게 보고한다.

기본 양식의 열: 테스트 케이스 ID, 테스트 베이시스 ID, 테스트 목적, 사전조건, 입력값, 절차, 예상 출력값, 사용한 테스트 기법, 제안, 비고.

### 6. 보고

사용자에게 짧게 보고한다:
- 출력 파일 경로
- 베이시스 수, 조건 수, 기능/비기능 케이스 수, 제안 케이스 수, 커버리지
- 기법별 케이스 수 (PICT 사용 여부 포함)
- 질의 사항 (모호해서 기대값을 정할 수 없던 요구사항)
- 가정한 사항 (해상도, 테스트 환경 등)
