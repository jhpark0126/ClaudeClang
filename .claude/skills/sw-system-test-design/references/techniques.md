# 테스트 기법 상세

## 동치 클래스 분할

1. 각 입력(및 출력에 영향을 주는 상태)의 도메인을 적는다.
2. 요구사항상 같은 처리를 받는 값의 집합으로 나눈다: 유효 클래스, 무효 클래스.
   - 수치 범위 `[min, max]` → 유효 1개, 무효 2개(미만, 초과)
   - 열거형 → 처리 방식이 다른 값 그룹마다 1개, 정의되지 않은 값 1개
   - 신호 상태 → 유효, 무효(invalid flag), 타임아웃
3. 유효 클래스는 묶어서 최소 케이스로, 무효 클래스는 케이스당 하나.

예: "목표 온도 16.0~32.0 ℃ (0.5 ℃ 단위) 입력을 수용하고 범위 밖은 무시하고 이전 값 유지"
- EC1 유효 16.0~32.0 → 대표값 24.0 수용
- EC2 무효 < 16.0 → 10.0 무시, 이전 값 유지
- EC3 무효 > 32.0 → 40.0 무시, 이전 값 유지
- EC4 무효 해상도 위반 → 24.3 (요구사항이 정의할 때만; 정의 없으면 질의 사항)

## 경계값 분석

위 예에서 해상도 0.5 ℃:
- 하한: 15.5(무효), 16.0(유효) [3-value면 16.5 추가]
- 상한: 32.0(유효), 32.5(무효) [3-value면 31.5 추가]

경계값 케이스가 동치 클래스 대표값을 겸할 수 있으면 합친다 (예: 15.5 케이스가 EC2를 커버하면 10.0 케이스는 불필요할 수 있다 — 단, 극단값 처리가 다를 가능성이 있으면 남긴다). 기법 열에는 둘 다 적는다: `동치 클래스 분할, 경계값 분석`.

시간 경계도 경계값이다: 타임아웃 500 ms → 499 ms 내 수신(정상), 501 ms(타임아웃 처리). 측정 지터를 고려해 허용 오차를 적는다.

## 페어와이즈 (PICT)

PICT 모델 파일 예 (`hvac_model.txt`):

```
Mode:      Auto, Manual, Defrost
FanLevel:  0, 1, 4, 7
AC:        On, Off
Ignition:  ACC, ON
IF [Mode] = "Defrost" THEN [AC] = "On";
IF [Ignition] = "ACC" THEN [FanLevel] <= 1;
```

실행:

```
python scripts/pict_runner.py hvac_model.txt --json
```

옵션은 `--` 뒤에 PICT 인자로 넘긴다 (예: 3-wise `-- /o:3`, 시드 고정 `-- /r:42`는 매번 다른 결과를 원할 때만). 기본(시드 없음) 실행은 결정적이다.

규칙:
- 파라미터 값에는 동치 클래스 대표값/경계값을 쓴다. 모든 값을 넣지 않는다.
- 무효 값은 페어와이즈에 넣지 않는다 (무효 값끼리 섞이면 원인 판별 불가). 무효 값은 동치 클래스 케이스로 따로 검증한다. 꼭 넣어야 하면 PICT의 `~` 접두사(negative value)를 쓴다.
- 결과 각 행의 기대값은 요구사항에서 도출한다. 기대값을 정할 수 없는 조합이 나오면 제약이 빠진 것이다 — 모델을 고친다.
- JSON의 `pict_models`에 모델 텍스트와 결과 TSV를 넣고, 해당 케이스의 `notes`에 `PICT 모델 hvac_model 행 3` 처럼 출처를 적는다.

## WoW 검증 (엣지)

SKILL.md의 목록 외에 다음 질문으로 찾는다:
- 이 기능이 "처음" 실행될 때(부팅 직후, NVM 비어 있음)는?
- 입력이 "동시에" 들어오면? 우선순위가 정의되어 있는가?
- 입력이 "너무 자주" 바뀌면? 디바운스/히스테리시스가 있는가?
- 입력이 "멈추면"(갱신 없음, alive counter 고정)?
- 동작 "도중에" 상태가 바뀌면(모드 전환, 전원 저하)?
- 값이 "계속 쌓이면"(카운터, 로그, 큐) 상한에서?

각 WoW 케이스는 근거 요구사항의 기대 동작으로 판정 가능해야 한다. 판정 기준이 요구사항에 없으면 케이스 대신 질의 사항으로 보고한다.

## 상태 전이

요구사항이 상태 머신(모드, 시퀀스)을 정의하면 모든 유효 전이를 1회 이상(0-switch) 검증하고, 정의되지 않은 이벤트의 무시 여부를 확인한다. 기법 표기: `상태 전이`.
